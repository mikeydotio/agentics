# deployit: bare Xcode project layout

**Status:** implemented
**Plugin:** `plugins/deployit`
**Driver:** SCADPad (`/Volumes/Code/mikeyward/SCADPad`) could not be deployed at all.

## Problem

`_derive_metadata` recognises exactly two repo shapes, and **both require an
XcodeGen `project.yml`**:

| Layout | Signals | Metadata source |
|---|---|---|
| Apps-layout (Lillist) | `./<Name>.xcworkspace` + `./Apps/<Name>-<Platform>/project.yml` | the `project.yml` |
| Single-app (moshtail) | `./<Name>.xcodeproj` + `./project.yml` | the `project.yml` |

`project.yml` is an **XcodeGen** artifact. A hand-managed `.xcodeproj` — the
default for any project not generated by XcodeGen — has none, so deployit
refuses with *"no recognised Xcode project layout in cwd"* before it does any
build work. That refusal is not about signing, schemes, or platforms; it is
purely an inability to read two strings.

The two strings are `PRODUCT_BUNDLE_IDENTIFIER` and `MARKETING_VERSION`, and
the `.xcodeproj` already holds both. deployit was reading them from a
*generator's input file* instead of from the project itself.

## Non-goals

- Migrating consumers to XcodeGen. The dependency was deployit's, not the
  projects'.
- Changing how either existing layout resolves. Both keep precedence and
  behaviour exactly as before.
- Inferring the bundle id or version from anything other than Xcode. There is
  no regex fallback over `project.pbxproj`; that would be a second
  implementation of Xcode's own settings resolution, free to disagree with it.

## Design

Add a **third arm** to `_derive_metadata`, selected last:

```
workspace? + Apps/*/project.yml   -> Apps-layout        (unchanged, wins)
xcodeproj  + ./project.yml        -> single-app         (unchanged)
xcodeproj  + no project.yml       -> bare Xcode project (new)
otherwise                         -> fail
```

For the new arm:

- **Container.** Prefer a sibling `./<Name>.xcworkspace` when one exists, else
  the `.xcodeproj`. A workspace is what Xcode itself opens and what resolves
  local Swift package path dependencies; picking the `.xcodeproj` when a
  workspace is present would archive a different dependency graph than the
  developer sees.
- **Default scheme.** The `.xcodeproj` stem, matching the single-app arm.
- **`bundle_id` / `marketing_version`.** From
  `xcodebuild -showBuildSettings -json`, reusing `_settings_argv` so the query
  names the same binary, container, scheme and destination the archive will
  use. Asking xcodebuild is asking the only component whose answer is
  definitionally correct.
- **`project_yml`.** `null`. The key stays in the payload so existing readers
  keep their shape; a consumer that needs a path must handle `null`.

### Threading scheme and toolchain

The settings query must be resolved by the **same scheme and the same Xcode**
that will archive, or metadata can describe a different target or SDK than the
build. Two changes follow:

- `_derive_metadata(cwd, platform)` gains `scheme=None, env=None`.
- `cmd_deploy` resolves the per-project toolchain pin (`_read_project_config` →
  `_resolve_toolchain_developer_dir` → `build_env`) **before** calling
  `_derive_metadata`, and passes `args.scheme` and `build_env` in.

The other two arms ignore both parameters, so their behaviour is bit-identical.

### Failure mode

If `xcodebuild` cannot answer, or answers without one of the two settings, the
deploy **fails loudly** naming the container, the scheme and the missing key.
It never defaults, guesses, or falls back to the pbxproj — an unnamed bundle id
would publish a build under the wrong identity, and a wrong version would
mislabel it in the index and the GitHub release.

## Verification

`plugins/deployit/tests/test-metadata-bare-xcodeproj.sh` covers:

1. bare `.xcodeproj`, no workspace → `-project` container, settings-derived
   bundle id and version, `project_yml: null`
2. bare `.xcodeproj` **+** sibling `.xcworkspace` → `-workspace` container
3. `--scheme` override reaches the settings query argv
4. `xcodebuild` failing → loud refusal naming the scheme, not a silent default
5. existing layouts still win when a `project.yml` is present

`xcodebuild` is stubbed via `tests/fakes/`, matching the plugin's existing
`gh` / `tailscale` / `launchctl` fakes, so the suite stays hermetic.
